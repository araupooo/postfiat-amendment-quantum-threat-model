PFTL Amendment-State Probe: Quantum Threat Model for the Amendment Process

Which parts of the amendment process a harvest-now quantum adversary can attack, what each break would and would not buy, and where the process is structurally safe. Pinned tree: postfiatd main 0085a1ff885d6a446369cf73a4430f75af22be55. Live probe fetched 2026-11-13T23:02:58Z from the public read-only endpoints https://rpc.testnet.postfiat.org/ and https://vhs.testnet.postfiat.org/v1/network/ (no credentials, no writes, no live peer connections). Server: build 1.0.9, network_id 2025, validated ledger 8025564.

Headline finding. The amendment process is a threshold game over secp256k1 signatures, and the threshold is 67%, not 80%. With all 66 validators voting, forcing an amendment to a majority takes 45 broken validator keys under the live 67% rule (53 under the upstream 80% rule), and blocking a unanimous yes vote takes 22 (14 under 80%). The 67% rule therefore makes forcing easier and blocking harder than upstream — but the number that matters is still large, and no single broken key can do anything at all: one key is one vote, and the ledger records the majority, not the individual vote. The process has never been exercised live on this testnet: all 64 enabled amendments were enabled at a single ledger (86785, 2026-02-09T14:31:12.000Z) and no amendment currently holds a majority. The cheapest quantum attack is therefore not forging a majority at all — it is forging a majority for an unsupported amendment, which makes every node that does not support it halt with “server blocked”.

Reproduction

bash run_all.sh

Regenerates every derived output offline from the vendored sample (results/sample_amendment_data.json), rebuilds this page, and verifies digests. Expected: exit 0, byte-identical outputs. See REPRODUCTION.md for the exact command and recorded result, results/run_log.txt for the raw console log, and results/digest_check_output.txt for the raw digest-check output. Verify digests at any time with bash verify_digests.sh --check. To fetch a fresh live sample instead, run python3 harness.py --live first (public read-only endpoints, no credentials), then bash run_all.sh.

  • results/fetch_log.json — per-request fetch record
  • results/summary.json / summary.txt — derived measurements
  • results/amendment_table.csv, results/amendment_counts.csv, results/validator_sample.csv, results/validator_counts.csv, results/attack_path_counts.csv, results/ledger_sample.csv — per-record tables

Limitations

  • The live sample is a single point in time (2026-11-13T23:02:58Z); validator counts, ledger numbers, and amendment state move as the testnet advances. Offline reproduction re-derives from the vendored sample, not from a fresh fetch.
  • Thresholds are computed from the live counts and the pinned-tree threshold code; no ledger was compiled or run locally, and no validation was forged or replayed against a live node.
  • Validator public keys in the tables are public VHS data; no private key, seed, or credential appears anywhere in this pack.
